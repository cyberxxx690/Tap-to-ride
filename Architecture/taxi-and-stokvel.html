Two project briefs · pick one

Two cash economies, one problem each.

Both of these are real South African markets worth billions a year that run almost entirely on cash, and both are stuck for a reason a payments engineer can actually fix. You work on your own and you pick one. On Wednesday 23 September at 12:30 you show us what you built.

How this works
Stack
C# on Windows

Visual Studio 2022, .NET 9. Everything runs on your own PC — no cloud, no deployment, no phones, no mobile development of any kind.

You
On your own

One person, one brief, one repo. If someone else picks the same brief that's fine — you aren't competing, and two takes on the same problem is interesting to watch.

Data
Nothing real

No live card numbers, no real money, no customer data. Invent your own and make it look like Gauteng, not like a unit test.

The one date
Wed 23 Sept, 12:30

You present what you have. Roughly ten minutes each, then questions. Slides are optional. Something running is not.

One piece of advice, and it's the only one that really matters: get a thin version running early, then make it better. Ugly is fine. Hardcoded is fine. One screen is fine.

It is far easier to improve something that already runs than to finish something that never has — and it means that whatever else happens between now and the 23rd, you have something real to show. Build the skeleton, get it working end to end, then go back and put muscle on it.

Choose one

They are deliberately different problems. Taxi is about money moving when the network doesn't. Stokvel is about money that belongs to a group rather than a person. Neither is harder than the other; they fail in different places. Read both, then commit — swapping halfway will cost you more than sticking with the one you like less.

Brief 1 · offline & aggregation

Tap to Ride

Around fifteen million minibus taxi trips happen in this country every day and almost every one is paid in cash. It isn't because nobody has tried. It's because a R12 fare can't carry a card fee, and because there is no network inside a moving taxi on the N1 at half past six in the morning.

What you're actually proving

That a payment can be accepted with nothing on the other end of the line, held so it can't be tampered with, and settled later as one charge instead of nine — capped, so a rider is never surprised by what comes off their account.

The shape of it

You are building two programs that talk to each other, in one Visual Studio solution, both running on your own PC. That is the whole system. There is no phone anywhere in this brief.

Program 1

The fare terminal

What the driver holds. One screen, one job: identify a rider, take the fare, show a green tick in under a second whether or not the server is there — because a driver pulling into the rank will not wait for a spinner. Its own SQLite file. Shows a running count of trips not yet sent.

Program 2

The settlement server

An ASP.NET Core API with its own database. It receives batches of trips, groups them by rider by day, applies a daily cap, and produces one settled charge with the individual trips itemised inside it.

Between them

The queue

The part that is actually the product. Trips are written to disk and signed so they can't be edited afterwards. They go up on their own when the server returns. Sending the same batch twice must never charge a rider twice.

How "offline" works here

You don't simulate it and you don't need a phone. The terminal and the server are two separate processes, so you go offline by closing the server window. The terminal genuinely cannot reach anything — that is a real outage, not a mocked one, and it's more brutal than airplane mode because you can also kill the terminal itself and see whether the money survived. Add an in-app "no signal" toggle too if you want it for quick repeat testing, but on the day you close the actual server.

What "done" means
Must have

Without these there is no demo.

  • A terminal that records a fare with the server closed, in under a second, and says so on screen
  • Trips written to disk and signed, surviving the terminal being killed mid-shift
  • A batch endpoint that can receive the same batch twice without charging anyone twice
  • Aggregation into one settled charge per rider per day, with a daily cap applied
  • Seeded data that looks like real Gauteng routes, riders and taxis
Should have

Once the must-haves work, in this order.

  • A visible count of trips still sitting unsent on the terminal
  • Sync that fires by itself when the server comes back, not off a button you press
  • The individual trips visible inside the settled charge, itemised
  • An operator console: which terminals are online, how many trips are still out in the field, today's takings
Do not build

Out of scope. No marks, real cost.

  • A mobile app of any kind — no MAUI, no Android, no Xamarin
  • NFC, QR codes, card readers or any hardware. The rider types a code, and that's fine throughout.
  • A login or user accounts. Pick the driver from a dropdown.
  • A real card transaction or any payment-gateway integration
  • Anything cloud — no Azure, no hosting, no containers
The demo moment · rehearse exactly this
  1. Close the settlement server. Not a checkbox — the actual window, in front of the room.
  2. Take three fares on the terminal. Three green ticks. The counter reads 3 not sent.
  3. Now kill the terminal too, and reopen it. Still 3 not sent. Nothing was ever only in memory.
  4. Start the server. The trips go up on their own and one charge appears — capped — with all three itemised inside it.

Then do the thing that proves you understood the problem: send the same batch a second time on purpose, and show that the rider is still charged once. That is the moment the room realises you built the hard part instead of the screen.

Stack
ASP.NET Core minimal API Blazor Server · terminal EF Core + SQLite ×2 Blazor Server · console Optional: WinForms or WPF terminal

Three projects in one solution, all C# in Visual Studio. The terminal is easiest as its own Blazor Server app — it's still a separate process with its own database, and it's the same skills as the server. If you'd rather it were a real desktop window, WinForms or WPF is completely acceptable and changes nothing about the brief. Make that choice early and don't revisit it. "Signed" means an HMAC over the trip fields with a shared key — about twenty lines, not a research project.

Words you'll need
Idempotent
Doing it twice has the same effect as doing it once. Send the same batch five times, the rider is charged once.
Batch
A bundle of trips the terminal sends up in one go, with an ID of its own so the server can recognise a repeat.
Aggregation
Rolling many small trips into one charge, so nine R12 fares become a single R108 line instead of nine card fees.
Daily cap
A ceiling on what one rider can be charged in a day. Say R50: ride nine times, still pay R50.
Settlement
The point where the queued trips become one real, final charge that the rider would actually see.
A sensible order to build it in

This is not a schedule — there's one date and it's the 23rd. It's just the order that tends to hurt least, and each step has a way of knowing you're actually finished with it.

01

The server, with no screen at all

Trip and Batch models, the batch endpoint, aggregation by rider by day, the daily cap, and an idempotency key from your very first commit. Prove all of it from a .http file in Visual Studio. Resist building any UI at this stage.

Done when: you POST the same batch twice and the total does not move.

02

The terminal and the queue

The fare screen, the local SQLite queue, and sync when the server comes back. The rider is identified by a code typed in by hand — that is completely fine and it can stay that way. This is the point where you have a real demo, and everything after it is an improvement to something that already runs.

Done when: server closed → three fares → server opened → one capped charge.

03

Break it on purpose

Kill the terminal mid-shift and restart it. Send the same batch twice. Take nine trips and watch the cap hold. Take a fare, close the server, take another, reopen it. Write these four down as a checklist and re-run the whole list whenever you change something — this is the difference between something that works and something that worked once.

Done when: all four pass twice in a row, from a cold start.

04

The operator console

Terminals online, trips still out in the field, takings so far today. It's the thing that makes this look like a product rather than an experiment — but only once step 03 is genuinely solid, because a console in front of a broken queue is worth nothing.

Done when: you can watch the unsent count drop from the console as a terminal syncs.

05

Stop building, and rehearse

Give yourself a clear cut-off before the 23rd and hold it, even with things half-finished. Then run the demo three times — out loud, standing up, with the server actually closed. Half-finished code you don't demo costs you nothing; a demo you've never run costs you everything.

Done when: you've run it start to finish three times without touching the code.

What will kill you

Building the screen first

The fare screen is a text box, a button and a number. The queue is the product. It is very easy to spend most of your time on the best-looking tenth of the problem and arrive with nothing behind it.

Leaving idempotency for later

On a bad network, retries are not an edge case — they are the normal path. Build it in at the start, while it is still a column and an if. Add it at the end and you are rewriting the aggregator at exactly the moment you should be rehearsing.

Testing with the server running

Every single rehearsal happens with the server closed. The one time you skip it is the one time your sync fires silently in the background, the trips are already up, and the demo has no moment left in it.

If you're flying
  • A daily cap that varies by route, because Bara to Joburg CBD is not the same fare as a local hop.
  • An end-of-shift report the driver actually gets, showing what the owner owes them.
  • Two terminals running at once against one server — the same rider taps in two different taxis in the same day, and the cap still has to hold across both.
  • Detect the rider who pays on the morning leg and never appears again. Either they walked home, or your fare logic has a hole in it.
Brief 2 · shared ledger

Stokvel in Your Pocket

More than R50-billion a year moves through stokvels and almost none of it touches a payment rail. It's cash in a tin, a WhatsApp group, and one person that everybody has to trust. Every wallet ever built assumes money has exactly one owner. This one doesn't.

What you're actually proving

That a balance can belong to a group — governed by rules the members agreed to up front, visible to everyone at the same instant, with a payout that happens because it is due rather than because someone was trusted to hand it over.

The shape of it

One ASP.NET Core web app, running on your own PC, opened in several browser windows side by side — each window is a different member of the same stokvel. That is your demo rig and it costs you nothing to set up.

Part 1

The group and its rules

Create a stokvel, add members, set the monthly contribution, the payout order and the payout date. The rules are agreed once and then enforced by the software instead of by the treasurer — that swap is the entire product.

Part 2

The live pot

Every window sees the same pot climbing at the same instant, with no refresh. Who has paid, who is behind, how many days are left. The visibility is the feature — so make it obvious, and make it fair to whoever is having a bad month.

Part 3

The payout and the ledger

On payout day it disburses to whoever's turn it is and moves the rotation on, without anyone pressing a button. Then a full history: every contribution, every payout, who, when, how much. It has to still settle an argument twelve months later.

What "done" means
Must have

Without these there is no demo.

  • Create a group, add members, set the contribution, the payout order and the payout date
  • Two or more browser windows on one pot, updating live with no refresh
  • Contributions recorded against a member and a cycle
  • A payout that fires because the date is due, goes to whoever's turn it is, and moves the rotation on
  • A ledger showing every contribution and payout: who, when, how much
Should have

Once the must-haves work, in this order.

  • Who has paid and who is behind, readable at a glance
  • A "roll the clock forward" control so you can reach payout day inside a ten-minute demo
  • The three hard cases handled: a missed month, a mid-cycle joiner, a short pot on payout day
  • Legible from the back of a room, four windows at once
Do not build

Out of scope. No marks, real cost.

  • A login or user accounts. Pick a member from a dropdown.
  • A mobile app of any kind, and no phones in the demo
  • Real money movement — no EFT, no card, no payment gateway
  • Email, SMS or push notifications
  • A background scheduler or Windows service. Your clock control does that job better.
The demo moment · rehearse exactly this
  1. Four browser windows side by side on one screen — four members of the same stokvel.
  2. Pay from one of them. The pot climbs on all four at the same instant. No refresh, no F5.
  3. Roll the clock forward to payout day and let it fire. One window fills with the whole pot, and the rotation quietly moves on to the next name.
  4. Hand your keyboard to someone in the room and let them pay in. It should need no explanation at all.

The line that lands is the one you say over step three: nobody had to be trusted with the tin. Every stokvel in the country has that problem and none of them have that sentence.

Stack
Blazor Server SignalR EF Core + SQLite ASP.NET Core

One project, C# in Visual Studio, nothing else installed. SignalR is why this brief is worth doing in C#: the everything-moves-at-once moment, which is a day of websocket plumbing in most stacks, is close to free in Blazor Server — it is already how the framework works. Spend the time you just saved on the rules, because the rules are the actual problem.

Words you'll need
Stokvel
A savings club. Everyone puts in a fixed amount each month, and each month one member takes the whole pot. Rotating credit, run on trust.
Cycle
One round of contributions — typically a month. Twelve members, twelve cycles, everyone gets one turn.
Rotation
The agreed order of whose turn it is to be paid out. The hardest thing in this brief lives here.
The pot
What's been paid in this cycle and not yet paid out. Twelve members at R500 is a R6 000 pot.
Ledger
The append-only record of every movement. You never edit it — a correction is a new entry, not a changed one.
A sensible order to build it in

This is not a schedule — there's one date and it's the 23rd. It's just the order that tends to hurt least, and each step has a way of knowing you're actually finished with it.

01

The rules, on paper before they're in code

Group, Member, Contribution, PayoutTurn, LedgerEntry. Settle the rotation before you write a single screen. Whose turn is it? What happens when someone misses a month? Does a member who is behind still take their payout? What if the pot is short on the day? Write your answers in a text file and commit it — you will change your mind later, and you'll want to see what you originally decided and why.

Done when: those four questions have written answers, and the model compiles.

02

Two windows, one pot

Blazor pages, SignalR wired up. Two browser windows on the same pot: one pays, both move instantly. That is the entire product in miniature, and once it works everything after it is an improvement to something that already runs.

Done when: two windows, one payment, both numbers move with no refresh.

03

The payout, and the cases that hurt

Disbursement when the date is due, driven by a clock you control. Then the full ledger. Then break it deliberately: a member misses a month; a member joins halfway through the cycle; payout day arrives and the pot is short. Those three are where real stokvels actually fall apart, and handling them is the reason this brief is worth doing.

Done when: all three cases do something sensible and the ledger explains what happened.

04

Make four windows readable

This will be seen as four windows on one screen from the back of a room. Big numbers, obvious names, no chrome, nothing that needs squinting at. It's the cheapest possible improvement to how the whole thing lands.

Done when: you can read all four windows standing well back from the screen.

05

Stop building, and rehearse

Give yourself a clear cut-off before the 23rd and hold it, even with things half-finished. Then run it three times with four windows actually open — arranging windows live while people watch is thirty seconds you won't want to spend.

Done when: you've run it start to finish three times without touching the code.

What will kill you

Building screens before the rotation logic

"Whose turn is it, and what if they haven't paid" is the only genuinely hard thing in this brief. Everything else is forms. Left until the end, it reliably takes far longer than anybody expects it to.

Using DateTime.Now anywhere

A ten-minute demo cannot wait a month for payout day. Make "today" a value you control from your very first commit — one clock object you can move forward. Retrofitting that later means touching every file you've written.

Building a login

Don't. A dropdown of members is enough. Nobody in that room is going to ask how you authenticated, and every hour spent on identity is an hour not spent on the thing they came to see.

If you're flying
  • Let two members swap payout turns — somebody's car always breaks in the wrong month.
  • A grocery stokvel, where the payout goes to a merchant instead of a member and comes back as stock.
  • A member leaves mid-cycle having already taken their payout. Work out what's fair, then defend it.
  • The message the group sees when somebody falls behind. Write it kindly — that wording is the difference between a stokvel that survives and one that doesn't.
The 23rd

Wednesday 23 September, 12:30. Roughly ten minutes each, then questions. Show the thing running first and explain it afterwards — the demo is the argument, everything else is commentary. Here's what we'll be paying attention to.

  1. Did it run, live, on the day

    Not a recording, not a screenshot. Something actually working in front of people. This is worth more than any amount of scope.

  2. Did you build the hard part, or fake it

    The offline queue. The rotation rules. That is the bit we'll be looking at — a beautiful screen in front of a stub is worth less than a plain screen in front of something real.

  3. Can you say in one sentence why anyone would pay for this

    If it takes a paragraph, you haven't found the product yet. Write the sentence down on day one and keep improving it.

  4. What did you learn that nobody told you

    Time inside a real payments problem should leave you with an opinion. Bring it, even if it's that the brief was wrong about something.

Not judged on: how pretty it is (clean is plenty), test coverage, how much of the "should have" list you got through, or which of the two briefs you picked.

When you get stuck

You will get stuck, and some of this will be things you have never done before. That is the point — nobody handed you a brief you already know how to finish.

Being stuck for half an hour is normal. Being stuck for half a day without asking anybody is not. Ask early, ask in plain language, and say what you already tried. There's no prize for suffering quietly, and there is a real cost to it on the 23rd.

Organiser's checklist · not intern-facing

Before the briefing on the 17th

They should spend their first hours on the problem, not on installers. Everything lost to setup at the start comes straight out of what they can show on the 23rd.

  • Visual Studio 2022 (17.12+) and the .NET 9 SDK on every machineInstalled, opened at least once, and a File → New → Blazor project run successfully. Not "downloaded".
  • ASP.NET and web development workload, plus EF Core toolsdotnet tool install --global dotnet-ef. No MAUI, no Android SDK, no mobile workload is needed for either brief.
  • A starter solution, committed, handed to themSolution + web project + SQLite wired up + one migration that runs + one page that reads one row. Hand it over; don't make them build scaffolding.
  • A repo each, and permission to push to itThey work alone, so one repo per intern. Sort access out before the briefing, not during it.
  • Localhost HTTPS certificates trusteddotnet dev-certs https --trust on every machine — a five-minute fix that reliably costs a beginner two hours.
  • Taxi only — confirm two apps can run at onceMultiple startup projects in one solution, on different ports. Prove it once yourself so you can unblock them in a minute.
  • A named person they're allowed to interruptThe "when you get stuck" section above is a promise to them; make sure it's true.
  • Room booked for the 23rd at 12:30, with a projector or big screenThey'll be showing several windows side by side on one laptop, so check the resolution is legible from the back.
Notes on the scope

Both briefs are sized so that one person working alone can reach the must-haves without drama, and the should-haves if things go well. That's why the operator console (taxi) and the three hard cases (stokvel) sit in "should have". If anyone ends up pairing, promote both of those to "must" — otherwise they'll finish early and start gold-plating.

There's deliberately no day-by-day plan in here. The one thing worth watching for is somebody who hasn't got anything running end to end yet — that's the only early signal that matters, and it's much cheaper to catch in the first few days than in the last one.
